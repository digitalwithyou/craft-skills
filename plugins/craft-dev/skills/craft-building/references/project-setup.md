# Project setup for AI assistants

One-time setup per project so the dev skills and the content skills work, whichever assistant is used: Claude (Claude Code, Claude Desktop, claude.ai) or ChatGPT (Codex, ChatGPT). Requires Craft 5.12+ for MCP.

## Contents

- Files to add to the repo
- AGENTS.md template (and CLAUDE.md)
- config/mcp.php
- docs/ai/instructions.md
- Connecting developer tools: Claude Code and Codex
- Enabling MCP per environment
- The "AI drafts" user group
- Clients: Claude or ChatGPT

## Files to add to the repo

```
AGENTS.md                     project facts for every coding agent (Codex reads it directly)
CLAUDE.md                     one line, "@AGENTS.md", so Claude Code loads the same file
.mcp.json                     MCP servers for Claude Code (no secrets in it)
config/mcp.php                Craft MCP config: instructions loaded from docs/ai/
docs/ai/instructions.md       condensed brief served to every MCP client
docs/brand/voice.md           from craft-brand-discovery
docs/brand/visual.md          from craft-brand-discovery
docs/content/strategy.md      from craft-brand-discovery
docs/content/glossary.md      NL/EN/FR terminology
docs/content/pages/           page briefs from craft-preparing-pages
```

`docs/` sits outside `web/`, so nothing in it is publicly served. Codex keeps its MCP servers in `~/.codex/config.toml` (per user, not in the repo; see below).

## AGENTS.md template (and CLAUDE.md)

Write the project facts once in `AGENTS.md`. `CLAUDE.md` contains only `@AGENTS.md`, which Claude Code expands as an import.

```markdown
# <Project> — Craft CMS

Follows the Craft conventions (craft-dev skills: craft-building, craft-maintaining). Deviations below win over the spec.

## Facts
- Craft <version> <edition>; PHP <x>; sites: nl (primary), en, fr
- Hosting: Ploi on <provider>; staging: <url>; production: <url>
- Cache: <Blitz | Cloudflare | both>; SEO: <SEOmatic | the conventions' _seo.twig>
- Forms: Formie
- In-house plugins: <list>

## Deploy
<the actual Ploi deploy script steps, including where web/dist is built>

## Deviations from the conventions
- <none | list>

## Content
- Brand and voice: docs/brand/; strategy: docs/content/strategy.md
- MCP servers: craft-local-admin, craft-local, craft-staging, craft-production; production writes are drafts only

## Git
Commit messages follow the EC component library git conventions (https://ec.europa.eu/component-library/v1.15.0/eu/docs/conventions/git/):
- Header `<type>(<scope>): <subject>`; type is one of feat, fix, docs, style, refactor, perf, test, chore
- Scope optional: the part affected (`deps`, `page-builder`, `pageBlockFaq`, `vite`, a plugin handle)
- Subject: imperative present tense, lowercase first letter, no period at the end
- One line only, no body or footer; at most 100 characters
- Put what matters in the subject: advisory IDs (`… (GHSA-xxxx)`), breaking changes (`… (breaking: …)`), issue numbers (`… (#12)`)
- Reverts: `revert: <original header>`

## Lessons
<!-- One line per trap that changes what the next run does. Added by the craft-maintaining skill. -->
```

## config/mcp.php

Prefixes the instructions with the environment so assistants can confirm where they are before writing.

```php
<?php

use craft\config\McpConfig;
use craft\helpers\App;

$environment = App::env('CRAFT_ENVIRONMENT') ?? App::env('ENVIRONMENT') ?? 'unknown';
$file = dirname(__DIR__) . '/docs/ai/instructions.md';
$brief = is_file($file) ? file_get_contents($file) : '';

return McpConfig::create()
    ->instructions("ENVIRONMENT: {$environment}\n\n{$brief}");
```

## docs/ai/instructions.md

Keep it under ~1,000 words: it is sent at the start of every MCP session, to Claude and ChatGPT alike. Generated by craft-brand-discovery and updated by craft-building when blocks change.

```markdown
# <Site> — instructions for AI assistants

## Rules
- Never publish, delete or change live content. Create drafts only; the client publishes.
- Primary language: Dutch (Belgium). English and French are translated from Dutch.

## The site in three lines
<purpose, audiences, primary actions>

## Voice (summary)
<5–8 bullets from docs/brand/voice.md; words to use and avoid>

## Content model
- Pages live in the `pages` structure; almost every page is `pageGeneric` built from `pageBuilder` blocks.
- Repeated fragments are `sharedBlocks` entries, inserted with `pageBlockSharedBlock`.
- Navigation and footer are global sets; never edit them without being asked.

## Block catalog
| Block | Use it for | Don't use it for | Fields |
|---|---|---|---|
| pageBlockRichText | running text with headings | layouts, cards | heading, text |
| … | | | |
```

Build the block catalog from the editor manual (`modules/manual/content/<lang>/blocks/*.md`) and the builder Matrix entry types.

## Connecting developer tools: Claude Code and Codex

Use the same four server names in both tools so the skills and `AGENTS.md` can refer to them:

| Server | Transport | Signs in as | Use |
|---|---|---|---|
| `craft-local-admin` | stdio via DDEV | `admin` | schema work in dev only |
| `craft-local` | stdio via DDEV | `ai-drafts` | testing content work locally |
| `craft-staging` | HTTP + OAuth | the developer's `ai-drafts` account | review drafts for clients |
| `craft-production` | HTTP + OAuth | the developer's `ai-drafts` account | production drafts |

**Claude Code**: `.mcp.json` in the project root (committed, no secrets):

```json
{
  "mcpServers": {
    "craft-local-admin": {
      "command": "ddev",
      "args": ["exec", "php", "craft", "mcp/serve", "--user=admin"]
    },
    "craft-local": {
      "command": "ddev",
      "args": ["exec", "php", "craft", "mcp/serve", "--user=ai-drafts"]
    },
    "craft-staging": {
      "type": "http",
      "url": "https://staging.example.be/admin/mcp"
    },
    "craft-production": {
      "type": "http",
      "url": "https://www.example.be/admin/mcp"
    }
  }
}
```

Claude Code runs the OAuth sign-in the first time a server is used.

**Codex**: `~/.codex/config.toml` (per user). Prefix the names with the project when you work on several sites (`acme-craft-staging`).

```toml
[mcp_servers.craft-local-admin]
command = "bash"
args = ["-c", "cd /path/to/project && ddev exec php craft mcp/serve --user=admin"]

[mcp_servers.craft-staging]
url = "https://staging.example.be/admin/mcp"

[mcp_servers.craft-production]
url = "https://www.example.be/admin/mcp"
```

Then sign in once per HTTP server: `codex mcp login craft-staging`.

In Claude Code, the craft-dev plugin also installs a guard hook: it denies composer/npm/npx/craft commands that bypass DDEV and asks before hand edits to `config/project/*.yaml`. It's silent otherwise. Codex has no equivalent here; the skill rules still apply.

Notes for both:

- The authenticated endpoint defaults to `/{cpTrigger}/mcp` (`/admin/mcp` with the default trigger).
- stdio runs as the given user with no OAuth narrowing: use `admin` only for schema work in dev, `ai-drafts` for content tests.
- Never commit tokens.

## Enabling MCP per environment

- Settings → MCP is stored in project config: enable the **authenticated** HTTP server in dev and commit; it is applied to staging and production on deploy. Leave the public server off unless a project needs it.
- Generate OAuth signing keys on each environment: `php craft oauth/generate-keys` (dev: `ddev craft oauth/generate-keys`). Keep keys out of git.
- Behind Cloudflare or Blitz: exclude `/admin/mcp*` and `/.well-known/*` from caching.
- Multiple web servers: MCP handshake sessions are cached for an hour; use a shared cache backend.

## The "AI drafts" user group

Craft enforces "drafts only" through permissions, so a prompt mistake can't publish, whichever assistant is connected. Requires Craft **Pro** (Solo has a single admin user; Team has a single group, so check that it fits). On **Solo** sites, MCP clients act as the admin: rely on the skill rules, choose the "Read and write" access level, never "Full access", and tell the client the guard is procedural only.

Group `aiDrafts`, per content section (`pages`, channels, `sharedBlocks`):

- View entries ✔, Create entries ✔, **Save entries ✘** (this is what publishes live changes)
- Delete entries ✘; View other users' entries ✔; Save other users' entries ✘
- View other users' drafts ✔; Save other users' drafts ✔ (so assistants can continue a draft)
- Assets: view + upload to the content volumes; no delete
- Global sets: no edit permission (navigation and footer stay manual) unless the client wants it
- Access the control panel ✔ (needed to authorize MCP on the CP endpoint)

Users: `ai-drafts` for the developer's own local/staging/production work, plus one `<name> (AI)` account per client person who uses an assistant. They sign in with that account when authorizing the connection.

Test once per project: as `ai-drafts`, try to save the canonical version of a page via MCP and confirm Craft refuses.

## Clients: Claude or ChatGPT

Clients pick the assistant they already pay for. Same skills, same Craft connection, same drafts-only account.

| Step | Claude (claude.ai, Claude Desktop) | ChatGPT |
|---|---|---|
| 1. Install the skills | Add the marketplace (`digitalwithyou/craft-skills`) under Customize → Plugins and install `craft-content`, or upload the skill zips under Customize → Skills | Upload the skill zips under Skills → Create → Upload from your computer |
| 2. Connect the site | Add a custom connector per environment: `<Site> (staging)` / `<Site> (productie)` with URL `https://…/admin/mcp` | Enable Developer mode, then create an app per environment with the same name and URL, authentication OAuth |
| 3. Sign in | With the `(AI)` Craft account, access level "Read and write" | Same |
| 4. Use it | "Bereid een nieuwe pagina 'Renovatie' voor op staging" | Same; ChatGPT asks to confirm each write |

Plan requirements to check with the client:

- **Claude**: skills and custom connectors are available on the paid plans; check that the client's plan allows custom connectors.
- **ChatGPT**: writing through MCP (creating drafts) needs a Business, Enterprise or Edu workspace, where an admin enables Developer mode. On Plus and Pro, custom connections are read-only: the client can still run discovery and prepare briefs and copy, and the developer (or the client, by hand) puts the content into Craft.

Access can be revoked any time under My Account → Tokens in Craft.
